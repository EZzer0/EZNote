# 抖音打开慢排查记录

> [!info] 背景
> 2026-09-30，`https://www.douyin.com/?recommend=1` 打开明显缓慢，**其他网页正常**。
> 这句"其他网页没事"是整个排查的关键约束——说明不是带宽或链路整体劣化，要找的是**差异项**。

## 排查步骤与实测数据

### 1. 链路层：先证明或证伪"网络到抖音是坏的"

| 探测     | 命令/手段                         | 结果                                          | 结论                |
| -------- | --------------------------------- | --------------------------------------------- | ------------------- |
| ICMP     | `ping www.douyin.com`             | CNAME → 27.195.146.72，18–26ms，0 丢包        | 链路正常            |
| 逐段计时 | `curl -w` 看 DNS/connect/TLS/TTFB | DNS 17ms、TCP 37ms、TTFB 0.14s、72KB 共 0.17s | 服务器响应正常      |
| 横向对比 | 同法测百度/B站/腾讯               | TTFB 0.10–0.16s，同档                         | 抖音不比别人慢      |
| MTU      | `ping -f -l` 二分                 | 1464 通 / 1472 不通（百度 IP 一样）           | 路径 MTU≈1492，正常 |
| IPv6     | AAAA 解析 + v6 连接测试           | 有 AAAA，但本机无 v6 路由，35ms 立即失败      | 快速回退，非主因    |

> [!note] 一个一次性现象
> 首次 TLS 握手 1.45s，之后所有新进程连接均 ~0.05s——是冷握手/证书检查的一次性开销，**不是持续性慢**，不要被单次最大值带偏。

### 2. 浏览器层：headless 实测 + netlog 定量

- headless Edge 加载抖音 6 次：**1.0–2.4s**，与百度（0.9–1.6s）、B站（2.4–2.8s）、知乎（2.8–3.8s）同档
- 抓 netlog 逐事件分析：DNS 每次 17–25ms、主文档 143ms、**全链无 >60ms 的空洞**
- 但 netlog 里 Edge 自身后台请求（`edge.microsoft.com`、`clients2.google.com`）各占 **1.4s**——浏览器冷启动时和主页面抢资源

### 3. 找差异项：两个真正的嫌疑

**① UDP/443 被静默丢弃**
自造 QUIC 探测包发往抖音/百度/腾讯的 443 端口，全部超时无回包（B站 IP 回 ICMP unreachable，说明网络通、只是端口行为不同）。
→ Edge 收到 CDN 的 `alt-svc: h3` 宣告后会**先试 HTTP/3，超时才回退 TCP**，每次新连接白等一轮。

**② DNS 配置里藏着 8.8.8.8**

```text
WLAN DNS（手动静态配置）：114.114.114.114 + 8.8.8.8
DHCP 本该下发的：        192.168.1.1
```

| DNS 服务器          | 实测（冷查询）                   |
| ------------------- | -------------------------------- |
| 192.168.1.1（网关） | **9–11ms**                       |
| 114.114.114.114     | 15–26ms（偶发 213ms）            |
| 8.8.8.8             | **710–1684ms，部分查询 3s 超时** |

8.8.8.8 在国内被劫持/限速：一旦 114 应答失败就由它兜底，解析直接进秒级；Edge 还会因为系统里存在 8.8.8.8 而自动尝试 `dns.google` 的 DoH 升级，国内同样不通。

## 修复

提权 netsh 静态覆盖（当前 shell 非管理员，`Set-DnsClientServerAddress` 的 CIM 调用会被拒）：

```powershell
netsh interface ipv4 set dnsservers "WLAN" static 192.168.1.1 primary validate=no
netsh interface ipv4 add dnsservers "WLAN" 114.114.114.114 index=2 validate=no
ipconfig /flushdns
```

**改后验证**：冷缓存解析 12–26ms 全部命中、无超时，`8.8.8.8` 已移除。用户确认问题解决。

改回 DHCP 自动（撤销静态覆盖，需管理员）：

```powershell
Set-DnsClientServerAddress -InterfaceAlias WLAN -ResetServerAddresses
```

## 想法（方法论）

1. **先分层证伪，再猜原因。** 链路 → 协议 → 浏览器，每层用一条命令拿到数据再进下一层。如果一上来就怀疑"抖音服务器烂"，看到 ping 20ms 就该停了。
2. **一切结论要有输出背书。** "8.8.8.8 慢"不是感觉，是三次计时 + 一次超时换来的；给不出证据的怀疑就去跑命令，不脑内反复推翻自己。
3. **"其他网页没事"是最强的线索**，比任何绝对数值都有用——差异项（UDP 443、DNS 配置）藏在这里面。
4. **失败就换手段，不换排列硬试。** CIM 被拒 → 换 netsh → 还是拒 → `Start-Process -Verb RunAs` 提权，三步内到达。
5. **探测工具本身会产生假信号。** 自造 QUIC 包无回包 ≠ UDP 被墙（服务器可以合法忽略畸形包）——结论只取"全部目标都无回包 + 与 B站行为对照"的交集，并在笔记里标注证据强度。
6. **临时产物当次清场。** 4 个分析脚本、2.7MB netlog、4 个 headless 测试 Profile、残留进程，排查完一次性删掉，不留半成品。
